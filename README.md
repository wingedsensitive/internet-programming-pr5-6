# Обґрунтування використання семантичних HTML-елементів

Застосовано такі семантичні елементи:

- <section>
  Елемент "section" використано для виділення великих тематичних частин документа, кожна з яких має власний заголовок:

1. Щоденний виклик (`#main-challenge-title`) об'єднує головну вправу дня та статистику прогресу.
2. Списки слів (`#vocab-title`) групує окремі теми для вивчення лексики.
3. Таблиця слів для вивчення (`#word-section-title`) утворює окремий блок для практичної роботи з конкретними словами.

- <article>
  Елемент "article" застосовано для блоків, які є самодостатніми і зберігають свій сенс навіть у відриві від решти сторінки:

1. Картка з фразою дня "Get the hang of" (містить саму фразу, переклад, пояснення, приклад та кнопку для виконання вправи).
2. Картки категорій словника ("Розмовна англійська" та "Комп'ютерне обладнання"), кожна з яких має власну статистику проходження та посилання на відповідний розділ.

- <aside>
  Елемент "aside" використано для блоку "Your Statistic" (графік активності за тиждень). Цей блок є додатковою, довідковою інформацією, яка опосередковано пов'язана з основним контентом (вивченням англійської), але не є його критичною частиною.

- <div>
  У поточній розмітці елемент "div" не застосовувався, оскільки весь вміст вдалося логічно згрупувати за допомогою відповідних семантичних тегів (наприклад, "article", "section", "figure", "address").

- "<table>"
  Елемент "table" застосовано виключно за прямим призначенням — для відображення табличних даних (Слово, Переклад, Контекст, Статус). Таблиця не використовується для візуального позиціонування чи створення макета сторінки. Для забезпечення доступності використано елементи "caption", "thead", "tbody", "th" та атрибути "scope".

# Звіт з практичної роботи №4: Вебформи проєкту "GrammarFerret"
Опис діагностованих CSS-проблем за допомогою DevTools:

Перевизначення стилів (Каскад та специфічність)
Під час інспектування кнопки відправки форми (<button type="submit">) у DevTools (вкладка Styles) я виявила перекреслені (overridden) декларації. Базові стилі браузера та загальні стилі сторінки конфліктували з дизайном компонента. Перемогло наше правило із селектором .auth-form button[type="submit"]. DevTools показав, що цей селектор має вищу специфічність (клас + тег + атрибут), ніж просто селектор тегу button. Це дозволило застосувати правильний колір фону без використання крихких рішень на кшталт !important.

Діагностика блокової моделі (Box Model)
За допомогою вкладки Computed я перевірила блокову модель полів вводу (<input>). Задання 100% ширини разом із внутрішніми відступами (padding: 0.75rem 1rem) та рамкою (border) спочатку робило елемент ширшим за контейнер. Інспектор Box Model у DevTools наочно показав, що застосування глобального правила box-sizing: border-box змусило браузер включати padding та border у ці 100% ширини. Це дозволило уникнути появи горизонтального скролу та відмовитися від фіксованих значень width і height.

# Звіт з практичної роботи №5: Адаптивний вебінтерфейс GrammarFerret

## 1. Обрані Breakpoints та обґрунтування
* **Мобільний вигляд (базовий Mobile-First до 768px / 48rem):** Базовий стиль орієнтований на вузькі екрани смартфонів. Текст розгортається в одну колонку, навігація ховається у плаваючу кнопку (FAB), а таблиці отримують горизонтальний скрол через контейнер `.table-wrapper`.
* **Tablet / Desktop Breakpoint (`min-width: 48rem` / `768px`):** Обрано точки переходу на основі аналізу контенту. При досягненні 768px з'являється достатньо простору для відображення повної десктопної навігації в хедері та переходу дашборду у двоколонковий режим (`1.5fr 1fr`).
* **Desktop Wide (`min-width: 64rem` / `1024px`):** Збільшуються відступи у контейнері `main` для комфортного читання.

---

## 2. Використання Flexbox та Grid
* **Flexbox використано для:**
  * Шапки сайту (`header`) та навігаційного меню (`nav ul`).
  * Плаваючої кнопки мобільного меню (`.floating-menu-container`).
  * Внутрішнього вирівнювання елементів у картках (`.list-card`, `.card-actions`).
* **CSS Grid використано для:**
  * Двовимірного дашборду головної сторінки (`.dashboard-top`).
  * Адаптивної сітки списків слів (`.vocab-cards-grid`) з використанням `repeat(auto-fit, minmax(min(100%, 260px), 1fr))`.

---

## 3. Діагностовані та виправлені responsive-проблеми
1. **Проблема з горизонтальним переповненням таблиці:** На екранах екранах менше 480px широка таблиця слів розтягувала ширину всієї сторінки. **Рішення:** Таблицю огорнуто в блоковий контейнер `.table-wrapper` з властивістю `overflow-x: auto`.
2. **Незручні елементи керування для тачскрінів:** Малі розміри кнопок ускладнювали точне натискання на мобільних пристроях. **Рішення:** Для кнопок та полів вводу встановлено мінімальну висоту `min-height: 44px`.
3. **Невідповідність анімацій для користувачів із чутливістю до руху:** **Рішення:** Додано системний забіг `@media (prefers-reduced-motion: reduce)`, який вимикає анімації та плавну прокрутку.

---

## 4. Результати тестування
* **Перевірені ширини:** 320px, 390px, 768px, 1024px, 1280px.
* **Тест Zoom 200%:** Верстка зберігає структуру, текст підлаштовується під ширину контейнера без перекриття.

# Практична робота №6: Основи програмування мовою JavaScript

## Предметна область: Списки слів (Word Lists)
У цій роботі реалізовано бізнес-логіку для керування списками слів (Word Lists) без прив'язки до DOM. 

### Поля моделі (Model Fields)
Основна сутність проєкту представлена масивом об'єктів. Кожен об'єкт має таку структуру:
- `id` (Number): Унікальний ідентифікатор списку.
- `title` (String): Назва списку.
- `category` (String): Категорія списку (наприклад, "spoken", "tech", "general").
- `dailyGoal` (Number): Цільова кількість слів для вивчення на день.
- `progress` (Number): Відсоток вивченого (від 0 до 100).
- `isFavorite` (Boolean): Чи додано список до обраного.

## Контракти функцій (Contracts)

### Нормалізація та валідація
- **`normalizeTitle(value)`**
  - *Вхід:* `value` (Будь-який тип).
  - *Вихід:* Рядок (String) без зайвих пробілів. Якщо вхідний параметр не є рядком, повертає порожній рядок `""`.
- **`validateList(list)`**
  - *Вхід:* Об'єкт `list`.
  - *Вихід:* Об'єкт `{ isValid: Boolean, errors: Array }`. Повертає список помилок, якщо назва коротша за 3 символи або `dailyGoal` виходить за межі 1-50.

### Пошук, фільтрація та агрегація
- **`getListById(lists, id)`** 
  - *Вихід:* Повертає об'єкт списку або `undefined`, якщо id не знайдено.
- **`getListsByCategory(lists, category)`**
  - *Вихід:* Новий масив об'єктів, що відповідають вказаній категорії.
- **`getShortLabels(lists)`**
  - *Вихід:* Масив рядків у форматі "Назва (Прогрес%)".
- **`getTotalDailyGoal(lists)`**
  - *Вихід:* Число (Number). Сума всіх `dailyGoal`.
- **`hasCompletedLists(lists)`**
  - *Вихід:* Boolean. Перевіряє, чи є хоча б один список із прогресом 100%.

### Сортування (без мутацій)
- **`sortListsByTitle(lists)`** 
  - *Вихід:* Відсортований за алфавітом новий масив (з урахуванням української локалі).
- **`sortListsByProgress(lists)`**
  - *Вихід:* Відсортований за спаданням прогресу новий масив.

### Незмінювані CRUD-операції
- **`addList(lists, newList)`**
  - *Вихід:* Новий масив, що містить `newList`.
- **`updateList(lists, targetId, changes)`**
  - *Вихід:* Новий масив. Оновлює властивості об'єкта із заданим `targetId`. 
  - *Edge case:* Зміна `id` через `changes` ігнорується. Якщо `targetId` не знайдено, повертається копія оригінального масиву без змін.
- **`removeList(lists, targetId)`**
  - *Вихід:* Новий масив без об'єкта із заданим `targetId`. Якщо `targetId` не існує, повертається копія масиву.
